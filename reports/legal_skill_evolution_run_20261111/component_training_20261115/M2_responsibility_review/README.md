## 本地真实证据

当前大方向已经把法律程序执行交给确定性代码，8B主要读取事实。问题出在旧`source_economic_legal_ledger_b8`组件仍把四类工作合在一次读取：年度收入、付款、精确法律给定、一般法条边界表述。每条付款要求13个字段，其中又嵌套9个服务字段，另要求模型标记`is_query_payment`、`is_query_service`。这类目标记录对齐属于额外职责；旧读取还会携带问题和原生查询。新关系读取已能只给事实，但经济组件尚未接到这一接口。

实际SARA TRAIN的bb6记录中，原文明示工资3200美元和服务期间2017-02-01至2017-09-02。8B输出付款`temporal_precision=unstated`、`payment_date=null`，却又填`stated_year=2017`。服务年份不能自动当成付款年份；不能将它改成虚构的付款日期来通过。

该请求2043输入token、419输出token，stop，既未截断也未达到上下文上限。因此证据支持的是**语义职责混杂**，不是提示太长。只凭一案仍不能量化“任务数量”单独造成多少损失。

付款转换器先验证整条记录的时间一致性，再输出`payment_`等事实。该时间冲突使它直接跳过付款，返回一个笼统的`one_or_more_records_unread_or_invalid`，而非付款事件、角色和时间各自的状态。原生求解器此时首个阻断是`payment_`未读。局部服务/地点正确，不能弥补付款事件没有进入程序。

**进一步定位也否定了“补一个付款存在字段就整案好了”。** 仅把原文明确的付款核心作为人工定位探针送入同一原生程序，日期与年份仍保持未读，接着暴露`means_(付款)`、`plan_(Bob)`和`end_(服务)`三个未读范围。探针仍未解决，未计作模型输出、主路径成功或方法收益。它说明需要逐步执行、逐步补齐实际需求，而不是全局关闭完整性检查。

## 当前采用的修复方向

8B读取**当前事实中的一个有共享事件键的关系元组及证据**。付款与服务分开；付款人、收款人等关联角色仍属于同一事件，不能拆成无连接的零散字段。题目目标的符号标识对齐、确定性的格式转换、合法的变量合一与程序执行交给代码；没有明确依据时保留未知。

将经济组件接到已有关系契约接口，分别表示付款核心、付款时间、年度收入和精确法律给定。付款时间失败不能自动抹掉独立证实的付款存在；同时不得把“时间未读”改成“原文确认没有时间”。字段/事件属性的完成范围必须随结果传递，程序真正访问未读范围时继续阻断。

反馈定位到实际记录、字段和转换条件，并附当前原生阻断；修订由教师学习观察表示、读取约束和转换，沿用既有真实8B验证与原TRAIN监督，选择以整案主路径及对应源检查为准。先复用已知合法部分，再针对实际残余读取，不原样反复请求，不要求无关字段全部齐全。

**模块化、符号执行和按目标补读都是近邻已有能力。** 这些修复不能单独当第二创新。仍须证明：（1）从错误学得的表示/转换相对固定小关系抽取及同信息普通教师有跨案作用；（2）同一契约下残余读取相对普通补读有额外效果或成本优势。现有否定结果不抹去，也不因本次查阅或定位探针标记Goal完成。

## 对本次问题的明确判断

8B的旧读取职责偏宽，但现有证据不能把整案失败全部归因于模型容量，也未做保持其他条件相同的职责数量因果实验。现在有三类已区分的原因：原始输出把服务时间混入付款时间，属于模型语义错误；转换器以整条记录/整组件为单位拒绝，属于结果衔接过粗；下一段真实程序仍访问未读事实，属于尚未完成的观察覆盖。2043/419 token的失败不是截断证据。正确做法是缩小语义职责并显式传递事件和字段状态，不能将日期填成猜测值或把未读改成已确认不存在。

因此沿用既定分工：教师学习及更新表示/读取约束/转导；8B从当前事实读取带证据的小关系；程序负责明确身份对齐、变量绑定、调度、转换及法律执行。更新选择必须看整案主路径和源检查，局部字段成绩只能辅助定位。同一案例可以经过数个小读取，是否增加耗时要按实际总调用/token统计，不能预言拆分一定更快。

本次核对还发现合同C路径的独立接口缺陷：当前语义操作已声明，但消费者与审查器未完整接通。该问题已在两臂读取结束后的安全边界作共同修复，以已有输出0调用回放及负例验证；不当作第二项学习收益。见[共同操作语义对齐及原始对照](../source_operator_alignment/README.md)。下一研究工作继续原定关系契约精化，不更换课题，不因为上述定位而认定两项贡献成立。
