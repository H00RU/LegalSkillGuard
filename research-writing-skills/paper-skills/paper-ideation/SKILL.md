# 找创新点：当月热点 × 多智能体

我们的论文按同一个公式长出来：

**自家多智能体底座 + 一到三个月内的一篇热点 + 两者接缝处的一个修补 + 主场理论的扩展名 + 当月的大叙事。**

方向不固定。技能、自博弈、技能内化、token 级信号、通信拓扑只是 2026 年下半年的热点。固定的只有两样：底座是多智能体系统，热点每个月重新调研。本文件里的具体热点、大词和论文都是历史例子，用的时候以当月调研为准。

这里只管从调研到选定 idea。选定之后的写作交给 paper-writing 及其分技能。

## 0. 三种用法

| 用户的说法 | 怎么走 |
|---|---|
| 这个月有什么热点、做月度调研 | 第 1 节出月度雷达，末尾给 2 到 3 个最值得做的组合 |
| 帮我想下一篇、找创新点 | 第 1 到 6 节全流程，交付 3 到 5 张排好序的候选 idea 卡 |
| X 加 Y 能不能做 | 从第 3 节的接缝测试开始，给判断、修补方案和要补查的文献 |

用户只给了底座或只给了热点时，另一半从当月雷达里配。在定时任务里运行时，只做雷达和候选排序，不等确认。

## 1. 月度热点雷达（每月一次）

热点会过期，所以每月重做。本月已有雷达就直接读。上月的雷达也读进来，对比哪些在升温、哪些冷了；手边没有时，在过往对话里搜“热点雷达”。

**时间窗**：近一到两个月。我们历来用一到三个月内的新作：够新，同行还没来得及把它接到多智能体上；又已有代码和最早的跟进，能复现，也能判断热度。

**扫描面要宽**，多智能体本身只是其中一类：
- LLM 强化学习：GRPO 变体、信用分配、过程奖励、token 级信号
- 自我改进：RSI、自博弈、自动出题与课程
- 技能、记忆、经验库、harness 的演化
- 工具使用与环境：MCP、A2A、代码和浏览器智能体
- 推理与测试时计算：验证器、早停、预算分配
- 效率与成本：token 开销、决策式模型、小模型编排
- 多智能体本身：拓扑、通信协议、组织与角色
- 评测：新基准、LLM 评审的可靠性
- 新模型形态和产品发布

**来源**：arXiv 各分类的新提交（cs.MA、cs.AI、cs.CL、cs.LG）；Hugging Face Daily Papers 和 alphaXiv 的热门榜；大厂与开源组的博客和发布；会议放榜和 OpenReview 上的高分投稿；Semantic Scholar 或 Google Scholar 上几周内的跟进与被引。扫描面大时，按类别分给子代理并行搜，每个子代理只回报核实过的条目。

**够不够热**，满足两条以上算热点：
- 几周内有 3 篇以上工作沿用或对比它
- 在 Hugging Face 或 alphaXiv 的榜上靠前
- 大厂或知名组出品，并且开源
- 代码的 star 增长快
- 概念词在新论文题目里成批出现

**逐条核实**：打开 arXiv 页面，确认标题、编号、提交日期和核心机制。核实不了的不进雷达。arXiv 编号前四位就是年月（2607 是 2026 年 7 月），时效可以直接算。

**给热点分型**，不同类型在公式里的位置不同：

| 类型 | 历史例子 | 在公式里的角色 |
|---|---|---|
| 机制型：一篇方法带来新能力或新信号 | SESA、PATS、MANTA、FlowBalance | 做 B |
| 范式型：新模型形态、新协议、新产品 | 决策式模型 Jev | 做 B，或改造底座的接口 |
| 概念型：领域里升温的大词 | RSI | 做叙事 |
| 理论工具 | GFlowNet、贝叶斯决策、HCA | 做粘合剂，选权威的，不追新 |

**雷达表**，每个热点一行：

| 热点 | 来源与日期 | 类型 | 带来的新能力或新问题 | 它默认的假设 | 原本作用在单模型、单智能体还是多智能体 | 能落到多智能体哪一层 | 可配的底座 | 热度证据 |
|---|---|---|---|---|---|---|---|---|

“它默认的假设”最重要，第 3 节的接缝就从这一列找。表后列出本月升温的大词，再给 2 到 3 个最值得做的组合，每个用一句话说清接缝在哪。

## 2. 选底座，配热点

**底座优先用自家系统**。代码、基准、主表版式、范文都能继承，新论文只需证明新加的那一维。底座也可以是外部热点本身：R²Orch 以 SESA 为底座、PATS 为 B，自家贡献的是编排层。

自家底座（每出一篇新论文补一行）：

| 底座 | 一句话 | 可补的地方 |
|---|---|---|
| FlowSteer（arXiv 2602.01664） | 强化学习训练的多轮工作流编排 | 编排的是算子，智能体之间没有通信；多样性靠奖励项约束 |
| SkillFlow | FlowSteer 加 TTB、后向策略和技能演化 | skill 是算子，不是会通信的主体 |
| EvoSteer（arXiv 2609.38661） | Director 交错编辑智能体图，AnchorTB 训练，技能配对检验 | 价值头靠执行特征和任务槽，执行完才有读数 |
| R2Flow | SkillFlow 加 R²TB 和验证器门控的贝叶斯技能演化，RSI 主线 | 待用户补充 |
| CollabFlow | Collab-Director 构造协作图，类型化通信，CTB，RSI 主线 | 待用户补充 |
| R²Orch | Proposer 出题、Director 建图的自博弈，技能脚手架逐步撤出，两层 RSI | Director 一侧沿用 GRPO，新目标在 Proposer 一侧 |
| EvoSteer 后续（进行中） | 决策式 Director，执行前检查，HindTB | 待定 |

**配对原则**：
1. **B 补 A 的一个短板**。CollabFlow 补的是 SkillFlow 的 skill 只是算子；EvoSteer 的后续换掉了执行完才有读数的价值头。
2. **把单体方法升到多智能体层**。热点常在单模型或单智能体上提出：PATS 作用在单个 LLM 上，FlowBalance 作用在单个回答的 token 上，SESA 作用在搜索智能体上。升到多智能体编排层，就会遇到原作者没碰到的问题，这正是接缝。多智能体里能接热点的层：
   - 编排者：决策、编辑、停止
   - 出题者：课程、自博弈
   - 执行智能体
   - 通信与拓扑：图结构、协议、信息可见性
   - 技能、记忆与脚手架
   - 训练目标与信用分配
   - 验证与评测
   - 运行时控制：早停、重做、预算
3. **一次加一到两个热点**。再多，主线就散了。
4. **查撞车**。搜“B + multi-agent”“B + orchestration”，看近两个月有没有人做过。有同期工作，就按同期工作定位，不和它做实验对比，或者换组合。

## 3. 接缝测试（核心）

把 B 搬到 A 上，问一句：**B 自带的哪条假设，在 A 里失效了？** 写成：

> B 假设 X；在 A 里 Y，所以 X 不成立，后果是 Z。

说不出来，就只是拼接，换组合。说得出来，修好它的那一处就是核心创新。它是 A 和 B 单独都做不到的，所以组合读起来不像拼接。

多智能体里常见的失效点，逐条对照：
- 训练时用的特权信息（参考答案、反馈），测试时拿不到
- 只有终局奖励，信用要在多步、多角色之间分
- 执行器有随机性，或者信号要等执行完才有
- 课程或自博弈把成功率钉在某个值附近，按成功率设的门控读到的就成了课程
- 系统自己在变（技能撤出、拓扑修订），变化前的估计在变化后失效
- B 只在推理时适配而不训练，或者只训练而不在运行中调整
- 智能体之间要通信，出现写冲突、信息可见性和协议语义的问题
- 多智能体调用次数多，B 的额外开销被放大

历史例子，只作参考：
- **R²Orch**：自博弈把成功率维持在一半附近，PATS 按成功率阈值撤技能，读到的成了课程而不是技能。修补是组内随机隐藏候选技能做配对对照，再做后验决策。另一处是可学习性在撤出技能后失效，于是改在撤出后的 Director 上算。
- **CollabFlow**：MANTA 在推理时让通信拓扑自适应，不更新权重；FlowSteer 能训练，但编排的是算子。修补是可学习的智能体协作。
- **EvoSteer 的后续**：FlowBalance 的信号要参考答案，测试时拿不到；逐步做符号门控，会把出错那一步推得最高；EvoSteer 的价值头执行完才有读数。修补是执行前在 Director 前缀上读流，验证器定总量，hindsight 定分配。

## 4. 用理论修接缝

每个修补都从一个权威结果出发，再写本文改了什么。这样组合在纸面上就是理论扩展。先用主场工具，接缝需要时再借：

| 工具 | 修什么样的接缝 | 历史用法 |
|---|---|---|
| 流平衡家族（TB、SubTB、DB） | 多样性；子轨迹信用；这个前缀接着做下去值多少 | TTB、AnchorTB、R²TB、CTB、HindTB |
| 贝叶斯证据（后验、贝叶斯自助法、贝叶斯决策、Thompson 采样） | 技能或组件的收录、保留、撤出 | R2Flow、R²Orch |
| 配对检验与族错误率控制 | 技能准入 | EvoSteer |
| 课程与 UED（learnability、regret） | 出题和选题 | R²Orch 的递归可学习性 |
| Hindsight Credit Assignment | 用事后信息分配信用 | HindTB |
| 双时间尺度随机逼近、PPO 近端步 | 内外两层循环一起训练 | R²Orch |
| 随机化对照（Neyman、Rubin） | 去混杂地估计效应 | R²Orch 的技能撤出 |
| 严格适当评分规则 | 让运行时的读数可信 | EvoSteer 后续的执行前检查 |

同一件工具换个作用对象，就是新东西。流平衡先后用在整条轨迹、子轨迹、协作图、Director 的类型化 token 上。

修补还要过两关：
- **成本**：token 和墙钟开销与同行同一量级。在理论或设计层面省，同时保住创新点。
- **讲得清**：能用一个手算小例子说明它为什么有效。自己都讲不清的修补，审稿人也不会信。

## 5. 命名、叙事、包装

**命名**
- 基础算法加修饰：TTB、AnchorTB、R²TB、CTB、递归可学习性。不造凭空的描述性名字。
- 查重：网络检索加 Google Scholar，投稿前再查一次。撞名是大忌。
- 别像借来的那篇。例如 TokenBalance 和 FlowBalance 只差一个词，容易读成它的变体。
- 系统名不带产品名。新造名词全文 3 到 4 个，其余用同行在用的术语。

**叙事**
- 挂当月升温的大词（2026 年 9 到 10 月是 RSI），写成系统本来就有的设计，不是事后加的外壳。
- 大词会变，每月在雷达里更新。

**包装**：想 idea 时是 A + B，写成论文是“领域问题 → 我们的范式”。
- 把接缝上升成同行普遍遇到的挑战，找 2 到 3 篇文献支撑。只在用了本文机制后才出现的问题不能当挑战，R²Orch 初稿的挑战就是因此被否的。
- 三个挑战对三个创新点（范式、支撑对象、机制），三个创新点是同一系统的三个侧面。工程实现不算创新。
- 借来的部分用括号形容词交代。正文和附录都不写“基于 X”“结合 X 与 Y”。
- 细则见 paper-writing。

## 6. 交付：候选 idea 卡

每次给 3 到 5 张，排好序，写明推荐理由，等用户选定再细化。

每张卡交付前先过三问，过不了的不交：
1. B 放到 A 上，哪条假设失效了？
2. 修补能否从一个权威结果出发，写成它的扩展？
3. 这个接缝能否说成同行普遍遇到的问题？

每张卡的格式：

```
### 候选 N：暂定名
- 一句话：
- 底座 A：补它的哪个短板
- 热点 B：标题、arXiv 编号、日期；它带来什么
- 升到多智能体：B 原本作用在哪，现在落到哪一层
- 接缝：B 假设 X；在 A 里 Y，所以……
- 修补：做法，配一个手算小例子
- 理论起点：权威结果和文献；本文改了什么
- 名字：候选名和查重结果
- 叙事：挂哪个大词，怎样写成系统本来就有的设计
- 三挑战三创新：一张对应表，每个挑战都有文献支撑
- 关键实验：每个创新点一个 RQ，指标用准确率、条数、曲线；先做哪些不用训练的离线检查（用已有日志）
- 成本：为什么和同行同一量级
- 风险：同期工作、实现难点、需要用户提供的数据或日志
```

卡片后附一张排序表（接缝是否清楚、补不补短板、理论是否现成、成本、代码复用度、撞车风险）和来源列表，每条都是核实过的链接。结果写成中文文档，用文件卡片发出。

## 7. 另一条线：把工具箱搬进新领域

JusticeAxis、ScienceClaw 走的是这条：把自家的技能演化和证据把关搬进一个新领域，再配一个基准。流程同上，B 换成一个领域问题。先查这个领域近期的基准和代表系统，再找现有系统在这个领域普遍失效的地方。

## 8. 交流习惯

- 回复用简洁中文，不用破折号，用短句。
- 讲方法用白话和手算小例子，不堆公式。
- 文献零幻觉：每篇都核实存在，拿不准的不写。
- 用户常用语音输入，同音错字按上下文理解，拿不准时用一句话说明自己的理解。
- 先给方案，用户确认后再展开。
